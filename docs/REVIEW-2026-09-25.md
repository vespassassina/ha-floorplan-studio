## Findings

### Major

**M1. An empty radar slot draws a target dot on the sensor.**
`src/core/render.ts:657-658`. `Number("")` is 0, and an empty LD2450 slot
reads 0/0. Both are finite, so the dot is drawn at the sensor's own
position. An idle radar with three pairs shows dots on itself, which reads as
"someone is here".
Confirmed with a scratch test: states `"0"/"0"` and `""/" "` gave two
`<circle class="target" cx="300" cy="300">`. The claim that ESPHome
reports 0/0 for an empty slot comes from its ld2450 component and was not
checked on hardware.
Fix: treat a blank state as NaN, and skip a pair where x and y are both 0.
Add a test for both cases.

**M2. The ESPHome snippet in the docs does not compile.**
`docs/card.md:170-174`. `target_count` is a `sensor` key of `ld2450`, not a
`binary_sensor` key. The presence keys are `has_target`,
`has_moving_target` and `has_still_target`. Anyone who copies the snippet
gets an ESPHome config error, and `binary_sensor.office_radar_occupancy`
never exists.
Confirmed by reading the snippet against the ESPHome ld2450 schema (from
memory; the ESPHome docs were not fetched).
Fix: `binary_sensor: - platform: ld2450` with
`has_target: {name: "Office radar occupancy"}`.

**M3. Save can go over HA's websocket message limit.**
`src/core/schema.ts:96` caps each floor's trace at 4 MiB, and
`src/editor/editor-app.ts:1711` sends the whole layout over the websocket.
aiohttp's default `max_msg_size` is 4 MiB, and HA's `websocket_api` does
not raise it (read in HA's source). One trace near the cap plus the plan, or
two traced floors, is over the limit. HA then drops the connection and the
save is lost. `docs/DECISIONS.md` (S7.11) records this as an unhandled
risk.
Not reproduced against a live HA.
Fix: in `save()`, measure `JSON.stringify(layout).length`. Above about
3.5 MB, refuse with a message that says what happened, why, and to shrink
or remove a trace. Or cap the total trace bytes across all floors.

### Minor

- **m1. The user is not told when autosave drops the trace.**
  `persist()` returns false, but its callers ignore that
  (`editor-app.ts:209`, `:392`, `:1710`). A reload before Save loses the
  image silently. Fix: set a status line when it returns false.
- **m2. The fade field accepts nonsense.** `config-editor.ts:152-153`:
  an empty field becomes 0, not the default, and negative values pass.
  Fix: an empty field means the default; clamp at 0 or more.
- **m3. Phones cannot scroll the page over the card.**
  `floorplan-studio-card.ts:90` sets `touch-action:none` on the zoomable
  SVG even at fit, and zoom is on by default. A swipe that starts on the
  plan does not scroll the dashboard. This was accepted in DECISIONS
  (S7.4), but with zoom on by default it hits every phone user. Consider
  `pan-y` at fit, or zoom off by default.
- **m4. Kiosk may not update the hold at once.** Read in the code, not
  reproduced. `bindDeviceActions` gets `longPress: !kiosk` only when the
  `<svg>` element is replaced (`floorplan-studio-card.ts:444-458`). A kiosk
  change that leaves the markup unchanged keeps the old hold until the next
  re-render.
- **m5. The docs screenshots are stale.** `docs/img/editor-overview.png`
  shows a stray "Test" floor tab. Neither it nor `card-overview.png` shows
  the new person, radar or vacuum.
- **m6. A label is clipped in the editor shot.** In `editor-blueprint`,
  "Garden pond" sits under the garden door and a pond vertex handle.
  Label placement (S7.1) ignores doors. Cosmetic.
- **m7. The trace image has no pointer-events rule.** `render.ts:409`
  draws `<image class="trace">` first and gives it no `data-*`, so today it
  acts like empty canvas. Per finding 18, add
  `.trace{pointer-events:none}` and a computed-style pair.
- **m8. The card loads trace images it never draws.** `ws_load` returns the
  whole layout, so each card downloads up to 4 MiB per traced floor on every
  dashboard load. Consider stripping `trace` for the card.
